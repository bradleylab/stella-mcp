# Stella MCP 0.8.0 — Diagram Rendering, Units Warnings, MCP Surface Polish

**Goal:** Let agents *see* the diagrams the layout engine produces, catch the most common box-model unit mistakes at validation time, and adopt the MCP-native affordances (annotations, resources, prompts) that make the server a better citizen in clients.

**Architecture:** SVG rendering is pure-stdlib string building in a new `render_svg.py` — no rasterization dependency in core. Units checks are conservative warning-tier heuristics added to the existing validator. MCP surface work touches only `server.py`/`tool_schemas.py` plus a minimum-version bump of the `mcp` dependency.

**Prerequisite:** 0.7.0 shipped (this plan assumes `delete_model`, CHANGELOG, and lockfile-based CI exist).

**Scope guard:** No PNG rasterization in core (decision point recorded in Task 1). No full dimensional analysis — heuristics only. No XMILE arrays.

### Task 1: `render_diagram` — SVG Output

**Files:**
- Create: `stella_mcp/render_svg.py`, `tests/test_render_svg.py`
- Modify: `stella_mcp/tool_schemas.py`, `stella_mcp/tool_handlers.py`, `README.md`

**Why:** The layout engine is the project's largest single investment, but neither the agent nor the user can check its output without opening Stella. SVG is the verification artifact: agents can read it, users can open it in any browser, and the README finally gets a screenshot.

**Visual vocabulary (match Stella's conventions so diagrams read correctly):**

| Element | Rendering |
|---|---|
| Stock | Rectangle at (x, y) with width/height from the model, name label beneath |
| Flow | Double-line "pipe" along `flow.points` (or straight from/to stock edges), valve glyph (bowtie) at the flow position, arrowhead at the destination |
| Source/sink (flow with no from/to stock) | Cloud glyph at the unattached end |
| Auxiliary | Circle, name label beneath |
| Connector | Quadratic Bézier arc from source to target, control point derived from `connector.angle` when set (fall back to straight midpoint offset), thin line, small arrowhead |
| Module box | Rounded rect using the module's box geometry and style fields (border_color, background, label_side) |

- [ ] **Step 1: Failing tests.** In `tests/test_render_svg.py`:
- `render_model_svg(model)` returns a string that `xml.etree.ElementTree.fromstring` parses (well-formed XML).
- Build a small model (2 stocks, 1 flow, 1 aux, 2 connectors, 1 module): assert the SVG contains one `<rect>` per stock, one `<circle>` per aux, expected `<path>`/`<line>` counts, and `<text>` labels with the display names.
- Determinism: two renders of the same model are byte-identical (no randomness, no timestamps — required for snapshot-style testing).
- ViewBox bounds: all element coordinates fall inside the computed viewBox with the configured margin.
- Special characters in variable names are XML-escaped (`xml.sax.saxutils.escape` everywhere user text enters the document).
- **Missing positions** (review finding): fresh models carry `None` coordinates until layout runs, and `auto_layout=False` must not crash — `render_model_svg` on a model with `None` positions raises a clear `ValueError` naming the unpositioned variables (the tool handler maps it to `invalid_input` with the hint "call with auto_layout=true"). With `auto_layout=True` (tool default) the same model renders.
- **Imported geometry** (review finding): `_auto_layout` preserves fixed/imported positions, so `auto_layout=true` does NOT guarantee overlap-free output for imported models. Test: two stocks at identical coordinates render without error (overlap is the user's data, not a renderer crash); a model with locked connector routing (`points_locked=True`) renders the stored waypoints rather than the computed arc.

- [ ] **Step 2: Implement `render_svg.py`.** Public surface:

```python
def render_model_svg(model: StellaModel, *, margin: float = 40.0) -> str: ...
```

Pure function, stdlib only. Compute viewBox from element bounding boxes + margin. Build with a small internal element-emitting helper (one function per element type, composed by `render_model_svg`) — keep each ≤ ~50 lines per the project structure rules. Colors: neutral defaults (black strokes, white fills) except module style fields, which come from the model.

- [ ] **Step 3: Tool schema + handler.** Tool `render_diagram`: optional `model_id`, optional `filepath` (writes the `.svg`; parent directory must exist — same path conventions as `save_model`), optional `auto_layout` (default `true`, same semantics as `save_model` — run layout before rendering so a freshly built model renders sensibly). Response: text summary + structured `{"model_id", "svg": "<svg ...>", "filepath": ...}`. Note in the schema description that the SVG is also returned inline so clients without file access can use it.

- [ ] **Step 4: README.** "Diagram Preview" section with example call. Generate an SVG of the `sir` template, commit it under `docs/images/sir.svg`, and embed it in the README — the rendered diagram is the project's best self-advertisement.

- [ ] **Step 5: Decision point — PNG.** Some clients can only display raster images. Do NOT add a rasterizer dependency silently. Record the options in the PR description: (a) SVG-only (current), (b) optional `render` extra with `cairosvg`, (c) leave conversion to the caller. Default to (a) unless the operator says otherwise.

### Task 2: Units Consistency Warnings

**Files:**
- Modify: `stella_mcp/validator.py`, `tests/` (new `tests/test_units_checks.py`)
- Modify: `README.md` (Validation section)

**Design principle:** warning-tier only, and conservative — a false "units inconsistent" warning trains agents to ignore the validator. Only fire when the check is near-certain.

Two checks:

1. **`units_missing`** (warning): a stock or flow has no `units` while at least one other stock/flow in the model does. Mixed-units models are where unit mistakes hide; a fully unitless model (common in teaching) stays silent. Auxiliaries are exempt (dimensionless parameters are routine).

2. **`units_inconsistent`** (warning): only for flows where **every attached stock has the same non-empty units** (review finding: a flow can connect two stocks, and a conversion flow between stocks with different units is legitimate — checking each attachment independently would false-positive on exactly those). For qualifying flows, expected flow units are `f"{stock_units}/{time_unit}"`. Comparison after conservative normalization only: lowercase, strip whitespace, singular/plural collapse on the time unit (`years` ≡ `year`, `days` ≡ `day`, etc. — a fixed table for the XMILE-conventional time units, not a stemming algorithm). If the flow's units don't contain a `/`, or the stock/time units don't match after normalization, warn with the expected form in the message: `Flow 'photosynthesis' has units 'GtC' but stock 'Atmosphere' (GtC) over time unit 'years' implies 'GtC/years'`. Anything the normalizer can't confidently parse → stay silent.

- [ ] **Step 1: Failing tests** in `tests/test_units_checks.py`: inconsistent flow fires; consistent flow (exact and plural-variant match) is silent; unitless-everywhere model is silent; one-united-stock model fires `units_missing` on the unitless flow; aux without units never warns; flow with units but stock without is silent for `units_inconsistent` (insufficient information ≠ inconsistency).

- [ ] **Step 2: Implement** `_check_units` in `ModelValidator`, registered in `validate()`. The time-unit plural table is a module-level constant with the source noted (XMILE spec sim_specs time units conventions).

- [ ] **Step 3: README Validation section** gains the two new bullet points. Run full suite — the built-in templates must validate clean (if a template trips the check, fix the *template's* units, which is a genuine catch, and say so in the commit).

```bash
git commit -m "feat: add units consistency validation warnings"
```

### Task 4: MCP Surface — Annotations, Resources, Prompts

**Files:**
- Modify: `pyproject.toml`, `stella_mcp/tool_schemas.py`, `stella_mcp/server.py`

- [ ] **Step 1: Bump the `mcp` floor — and test AT the floor.** `ToolAnnotations` and the resource/prompt decorators require a newer SDK than `mcp>=1.0.0`. Determine the actual minimum: find the release introducing `ToolAnnotations` in the python-sdk changelog (https://github.com/modelcontextprotocol/python-sdk/releases) — set `mcp>=<that version>` rather than guessing. Then verify the floor is real (review finding: `uv lock` resolves to the *latest* mcp, so the lockfile never exercises the declared minimum): run the suite once with the floor pinned, e.g. `uv run --with "mcp==<floor>" --extra dev python -m pytest`, and add that as a single non-matrix CI job so a future floor-breaking API use fails in CI instead of on a user's machine. Run `uv lock` after the pyproject change.

- [ ] **Step 2: Tool annotations.** In `tool_schemas.py`, add `annotations=ToolAnnotations(...)` to every tool:
- `readOnlyHint=True`: `list_models`, `list_variables`, `list_connectors`, `list_modules`, `list_templates`, `get_template_info`, `inspect_model`, `validate_model`.
- **NOT read-only** (review findings): `get_model_xml` — its handler calls `to_xml()`, which mutates layout state (`_auto_layout`, flow points, connector angles, `last_export_warnings`) even with `auto_layout=False`; annotating it read-only would be a lie as implemented. Either (a) make the handler export from a `copy.deepcopy` so it becomes genuinely read-only and annotate it, or (b) leave it unannotated — prefer (a), it also fixes the surprising behavior that previewing XML rewrites the diagram. `simulate` writes files via `save_results_csv`, and `render_diagram` via `filepath`; annotations are static, so neither gets `readOnlyHint` — give both `idempotentHint=True`.
- `destructiveHint=True`: `delete_variable`, `delete_module`, `delete_model`.
- Everything else: default (mutating, non-destructive). Test: iterate `build_tool_definitions()` and assert the read-only set matches an explicit expected list — a new tool added without an annotation decision should fail this test.

- [ ] **Step 3: Resources.** Register `@server.list_resources` / `@server.read_resource`:
- `stella://templates/{name}` — one resource per discovered template (builtin + user), mimeType `application/xml`, content = the raw `.stmx`.
- `stella://models/{model_id}` — one per session model, content = current XMILE export (permissive mode). **Export from a `copy.deepcopy`** — a resource read must not mutate the session model's layout state (same `to_xml()` mutation issue as `get_model_xml`; review finding).
Tests: list returns the 5 builtin templates; read of `stella://templates/sir` parses as XML; read of an unknown URI is a clean error; reading a model resource leaves the session model's positions unchanged.

- [ ] **Step 4: Prompt.** Register one prompt `build-stella-model` (args: `description` of the system to model) whose text encodes the README "Recommended Agent Workflow" — build (now via `build_model`), sync connectors, inspect+validate, simulate (if `sim` installed), render, save. This makes the workflow discoverable inside MCP clients instead of only in the README.
