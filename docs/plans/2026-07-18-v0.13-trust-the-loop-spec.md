# Stella MCP 0.13: Trust the Loop

Status: approved specification

Artifact readiness: implementation-ready

Target release: 0.13.0

## Objective

Strengthen the evidence and failure behavior behind Stella MCP's existing
build, import, edit, save, simulate, and agent workflows. Version 0.13 must
make the package explicit about which XMILE semantics it understands, preserve
unsupported content in permissive workflows where practical, refuse unsupported
semantics in strict workflows, and broaden the retained Stella and agent
evidence for the capabilities already shipped.

This is a hardening milestone. It must not present arrays, nested submodels, or
other newly detected constructs as implemented features.

## Approved Product Decision

Arrays and nested submodels are unsupported in 0.13.

- Strict import and strict export must reject models containing those
  semantics with structured, actionable errors.
- Permissive import and export must report explicit warnings and preserve the
  unsupported XML fragments required to round-trip the file where practical.
- Simulation and analysis must reject models carrying unsupported simulation
  semantics before invoking PySD.
- The package must not silently scalarize arrays, flatten nested models, or
  report such models as strict-compatible.

## Rationale and Current Evidence

Stella MCP 0.12 has deterministic MCP scenarios, Stella desktop layout
fixtures, a compatibility corpus, one Stella-to-PySD numeric parity case, and
one retained free-form agent run. Those artifacts establish that the shipped
surface works for the tested cases, but they do not establish broad XMILE or
numeric coverage.

A read-only probe of the MIT-licensed SDXorg `test-models` repository at commit
`21aab02739dc5187bc9564e4d3de14e575905d2f` found the following behavior on
0.12:

- `samples/SIR/SIR.stmx` and `samples/teacup/teacup.stmx` strict-import and
  simulate successfully.
- `samples/arrays/a2a/a2a.stmx` strict-imports despite carrying dimensions,
  then fails during simulation.
- `samples/bpowers-hares_and_lynxes_modules/model.stmx` contains module
  instances and additional top-level models; the current parser retains only
  the supported top-level auxiliaries and reports connector warnings.
- Several older upstream `.stmx` and `.xmile` files are not well-formed XML
  because they use an unbound namespace prefix. Supporting or repairing those
  files is not part of this milestone.

The current numeric comparator requires exact time labels. The upstream SIR
Stella export contains three-decimal time labels for a model whose time step is
`0.03125`, so exact label comparison fails even though the rows represent the
same unrounded time grid. The comparator must support an explicit,
non-interpolating rounded-label policy rather than applying an inferred
tolerance.

## Success Definition

The milestone is complete when:

1. Selected independently maintained Stella fixtures have pinned provenance,
   expected capability classifications, semantic round-trip evidence, and
   reproducible reports.
2. Unsupported arrays, nested models, and module instances can no longer pass
   strict compatibility checks.
3. Permissive round-trips retain the unsupported structures covered by the
   corpus, with warnings that state the editing and simulation limitations.
4. Numeric discrepancy evidence covers the existing accumulator plus nonlinear
   and cooling models with explicit time-alignment policies and no invented
   scientific pass threshold.
5. Stella-reserved identifiers are detected before desktop save, and bundled
   templates do not use identifiers confirmed to be renamed by Stella.
6. Agent evaluation protocol v2 reports workflow, semantic, artifact, and
   completion outcomes separately across repeated runs.
7. Existing deterministic MCP, layout, packaging, and release gates remain
   green.

## Workstream 1: Pinned External Compatibility Corpus

### Source and Vendoring Policy

Source repository: `https://github.com/SDXorg/test-models`

Vendor a selected subset of `SDXorg/test-models` under:

`tests/fixtures/external_corpus/sdxorg/`

The source repository is MIT-licensed. Include its license text and an
attribution file beside the fixtures. Do not depend on the network during
tests or CI. Every vendored file must have:

- upstream repository URL;
- upstream path;
- pinned commit;
- SHA-256 hash;
- license identifier;
- fixture role;
- expected parser, round-trip, simulation, and numeric statuses.

Do not vendor the complete upstream repository.

### Manifest Contract

Create `tests/fixtures/external_corpus/manifest.json` with a versioned schema.
Each fixture entry must declare:

- `id`, local path, source URL, upstream path, pinned commit, and SHA-256;
- source license and attribution path;
- construct tags such as `scalar`, `nonlinear`, `arrays`, `graphical_function`,
  `module_instance`, and `nested_model`;
- expected `strict_import`, `permissive_import`, `permissive_roundtrip`, and
  `simulation` outcomes;
- expected compatibility finding codes;
- numeric output metadata when a canonical output is present;
- whether Stella desktop acceptance is upstream evidence or evidence produced
  by this project.

Manifest tests must reject duplicate IDs, missing files, hash drift, missing
attribution, unknown status values, and unsupported entries without expected
finding codes.

## Workstream 2: XMILE Feature Detection and Safe Failure

### Feature Report

Add a focused module, `stella_mcp/xmile_features.py`, which inspects the parsed
ElementTree before conversion to `StellaModel`.

It must return a deterministic feature report containing findings with:

- stable code;
- support status: `supported`, `preserved_only`, or `invalid`;
- human-readable message;
- structural location or element path;
- count of matching elements.

The initial unsupported finding codes are:

- `xmile.arrays`: top-level `<dimensions>`, variable-level `<dimensions>`, or
  an explicit arrays declaration;
- `xmile.module_instances`: `<module>` declarations inside a model's
  `<variables>` section;
- `xmile.nested_models`: more than one direct top-level `<model>` element.

Do not classify logical groups represented by XMILE `<group>` elements as
module instances. Those are already supported by Stella MCP's logical module
feature.

### Parser Integration

Integrate detection into `parse_stmx_file()` immediately after XML parsing and
before conversion:

- In strict mode, raise one compatibility error that identifies every detected
  `preserved_only` feature code. Do not fail only on the first feature.
- In permissive mode, append stable warning messages and retain the feature
  report on the `StellaModel` instance.
- Preserve existing strict/permissive behavior for malformed values and broken
  supported references.
- XML syntax errors, including unbound namespace prefixes, remain parse errors;
  permissive mode must not repair malformed XML in 0.13.

Add a typed compatibility exception so MCP handlers can return a stable error
envelope:

- code: `unsupported_model_feature`;
- category: `compatibility`;
- details: finding codes and messages.

The public error must not include a Python traceback or backend exception text.

### Unsupported XML Preservation

Current preservation fields do not cover top-level dimensions, additional
top-level models, or unknown children of `<variables>`. Add explicit storage
for:

- root-level extra child XML;
- additional top-level model XML;
- variables-level extra child XML.

Export those fragments at their original structural levels and preserve their
relative order within each extra-fragment collection. Namespace declarations
must remain valid after export.

For the selected unsupported controls, permissive import followed by
permissive export must retain:

- the dimension declarations and variable dimension references;
- module instance declarations and their connection mappings;
- all additional top-level model definitions;
- the unsupported structures' names and equations as XML content.

Byte-for-byte XML identity is not required. Structural presence and the
supported semantic signature are required.

### Simulation and Analysis Guard

All PySD-backed paths must reject a model whose retained feature report contains
`preserved_only` simulation semantics. Put the guard at the shared simulation
compilation boundary so it covers:

- `simulate`;
- `compare_scenarios`;
- `sensitivity_analysis`;
- `calibrate`.

The error must list the unsupported feature codes and recommend strict import
for early validation. It must replace opaque downstream errors such as
`KeyError` or `IndexError` from PySD.

## Workstream 3: Semantic Round-Trip Fidelity

### Reusable Semantic Signature

Move the compatibility test's private semantic signature into a reusable
evaluation module. The signature must cover all supported model semantics:

- model name and simulation specifications;
- stock names, initial equations, units, non-negative flags, and flow links;
- flow names, equations, units, endpoints, non-negative flags, and graphical
  functions;
- auxiliary names, equations, units, and graphical functions;
- logical modules, membership, box geometry, and supported style fields;
- connectors, endpoints, UIDs, angles, locks, and routing points;
- supported view geometry for variables and flows.

Exclude transient warning lists and export/layout reports. Treat UUIDs as
metadata and report UUID changes separately so legacy fixtures without stable
UUID behavior do not contaminate semantic equality.

### Structured Difference

Implement a deterministic recursive comparator that emits changes as:

- `path` using JSON Pointer notation;
- `kind`: `added`, `removed`, or `changed`;
- `before` and `after` JSON-safe values.

Ordering must be stable. Corpus reports must include the difference rather than
only an assertion failure. Automated tests must still fail when a fixture
expected to preserve supported semantics produces a non-empty semantic diff.

### Editing-Fidelity Boundary

This milestone tests editing fidelity through import/export/re-import and
targeted edits to supported fields in externally authored models. Add cases
that modify one supported equation and one supported simulation setting in the
SIR or teacup fixture, then verify:

- the requested values changed;
- unrelated supported semantics did not change;
- strict export and re-import succeed;
- retained unsupported fragments are not involved in these supported-control
  edit cases.

A session history, undo stack, user-facing change journal, or new model-diff MCP
tool is not part of 0.13.

## Workstream 4: Numeric Fidelity Evidence

### Comparison Cases

Retain the existing Stella 4.1.1 accumulator parity artifact. Add reports for:

- SDX teacup, using its pinned Stella output;
- SDX SIR, using its pinned Stella output;
- package built-ins that already received Stella desktop layout acceptance:
  exponential growth, SIR, Lotka-Volterra, carbon cycle 2-box, and nutrient box
  2-box;
- one scalar graphical-function fixture derived from the existing graphical
  function simulation tests.

The package-built-in and scalar graphical-function cases require fresh Stella
Professional exports retained with application version, export date, model
hash, and output hash.

### Time Alignment Policy

Upgrade `evaluation.compare_runs` to schema version 2 while retaining exact
alignment as the default.

Supported policies:

1. `exact`: current behavior; numeric time values must be identical.
2. `rounded_reference_labels`: same row count, strictly increasing time columns,
   no interpolation, and each candidate label must equal the reference time
   quantized to a manifest-declared number of decimal places using decimal
   round-half-up behavior.

The rounded-label policy must:

- operate from the original CSV text, not binary floating-point formatting;
- require the decimal-place declaration in the fixture manifest;
- reject missing, duplicate, decreasing, or nonmatching time labels;
- report the maximum raw difference between unrounded reference times and
  parsed candidate labels;
- never infer a tolerance from the observed data.

Use `rounded_reference_labels` only for source exports whose retained text
demonstrates rounded labels, including the pinned SDX SIR export. Other cases
remain exact.

### Discrepancy Policy

Continue reporting per-variable maximum absolute and symmetric relative errors
and their times. Add row count, finite-value checks, engine versions, input and
output hashes, alignment policy, and all simulation warnings.

Do not add a scientific pass/fail tolerance in 0.13. CI must verify that reports
are reproducible, finite, complete, and generated from pinned inputs. A changed
raw discrepancy report requires explicit review but is not automatically called
scientifically acceptable.

### Simulation Result Metadata

Add additive structured metadata to every PySD-backed tool result:

- backend name and installed version;
- actual integration method used;
- model-declared integration method;
- unsupported-feature preflight status;
- warnings already produced by method and series checks.

Do not change the numerical method. PySD remains the optional simulation
backend and Euler remains its documented integration behavior.

## Workstream 5: Stella Identifier Safety

### Validation

Expose a shared, case-insensitive predicate based on a new
`STELLA_IDENTIFIER_RESERVED_TOKENS` set in `equation_parser.py`. Build that set
from the existing XMILE-spec and Stella-extension token sets. Keep
parser-compatibility-only aliases in `STELLA_RESERVED_TOKENS`, but exclude those
legacy aliases from identifier rejection unless a source later establishes that
Stella reserves them as identifiers.

Add validator category `reserved_identifier` for stocks, flows, and auxiliaries
whose normalized display names collide with a Stella/XMILE built-in token. The
message must name the variable, identify the collision, and recommend a
descriptive replacement. Do not automatically rename user variables.

### Export Behavior

- Permissive export warns and emits the requested name.
- Strict export rejects confirmed reserved-name collisions.
- Strict import rejects any model variable whose case-insensitive name is in
  `STELLA_IDENTIFIER_RESERVED_TOKENS`; permissive import warns and preserves the
  original name.

The initial regression cases must include `beta` and `gamma`, which Stella
Professional 4.1.1 renamed during the retained 0.12 desktop workflow.

### Bundled SIR Migration

Update the bundled SIR template and dependent fixtures:

- replace `beta` with `transmission_rate`;
- replace `gamma` with `recovery_rate`;
- update equations, connectors, agent scenarios, expected snapshots, diagrams,
  and documentation;
- retain the template's existing initial values, equations' mathematical
  meaning, simulation settings, and layout quality.

This is an identifier migration, not a change to the SIR method or parameter
values.

## Workstream 6: Agent Evaluation Protocol v2

### Scope

Upgrade `evaluation/agent_scenarios.json`, `agent_runner.py`, and
`agent_reporting.py` to protocol/report schema version 2. Preserve the existing
three workflow classes:

- construct, validate, simulate, render, and save a model;
- load and modify a template, then validate, simulate, render, and save;
- read and analyze a model with simulation, scenario comparison, sensitivity,
  and save.

Update prompts and checks for the SIR identifier migration and consistent time
unit wording.

### Outcome Dimensions

Score each scenario independently on:

- `workflow`: required phases completed in valid order;
- `semantic`: post-run model state satisfies the scenario contract;
- `artifacts`: required files exist, are non-empty, and have recorded hashes;
- `completion`: the agent returned a final response and did not stop at a round
  cap or backend failure;
- `tool_health`: MCP tool errors, including whether each was recovered.

Overall status is passed only when workflow, semantic, artifact, and completion
dimensions pass. Tool errors are reported separately; a recovered user-input
error does not erase a correct outcome, while an unrecovered error fails the
affected dimension.

### Semantic Expectations

Add explicit expectation operators instead of weakening exact checks globally:

- exact value;
- one-of values;
- normalized time-unit equality using the validator's documented calendar-unit
  mapping;
- finite numeric value;
- non-empty value.

The runner must reject unknown operators and malformed scenario definitions at
preflight.

### Repeated Evidence

Run each protocol scenario in three fresh MCP sessions using the previously
approved personal OpenAI routing. Record requested and resolved model names,
effective request settings, endpoint category, usage, duration, tool catalog
hash, and scenario hash for every run.

Aggregate raw pass counts by outcome dimension and scenario. Do not present
three repetitions as a statistically estimated general success rate.

Paid free-form runs remain a manual release evidence gate. CI tests the runner,
schema validation, scoring, redaction, reporting, and deterministic MCP
scenarios without calling an external model API.

### Catalog Discipline

Do not add modeling tools solely to improve the agent score. The full current
tool catalog remains the evaluation surface. Any tool addition discovered to
be necessary during implementation requires a separate scope decision and
must identify the observed failure it resolves.

## Workstream 7: Capability Matrix and Documentation

### Generated Evidence

Add an evaluator that combines external-corpus, round-trip, simulation, and
numeric records into:

- version-prefixed machine-readable JSON under `results/evaluation/`, following
  the existing `0.12.0-<artifact>` naming pattern;
- a concise Markdown capability matrix under `docs/evaluation/`.

The matrix must distinguish:

- parses in permissive mode;
- accepted in strict mode;
- supported semantics preserved;
- unsupported XML preserved;
- PySD simulation supported;
- Stella numeric evidence available;
- desktop open/run/save evidence available.

Generate the Markdown from JSON so the two artifacts cannot drift.

### User Documentation

Update README, architecture documentation, changelog, and release notes to state:

- what strict and permissive compatibility now mean;
- arrays and nested submodels are preserved-only and not simulated;
- which constructs have numeric evidence;
- how Stella-reserved names are handled;
- PySD's actual integration method and limitations;
- agent evidence is repeated descriptive evidence, not a universal success
  claim.

Avoid claims that the external corpus establishes compatibility with every
Stella or XMILE model.

## Desktop Acceptance Protocol

Desktop evidence remains an operator workflow because Stella Professional is
not available in headless CI.

For each new package-generated parity candidate:

1. Generate the `.stmx` from committed scripts or deterministic evaluator
   scenarios.
2. Open it in Stella Professional without a repair prompt.
3. Confirm expected variables and connectors are present and readable.
4. Run to the configured final time.
5. Export all compared variables at every model time step.
6. Save from Stella and re-import the saved file in strict mode.
7. Record application version, date, source model hash, output hash, identifier
   rename behavior, and operator notes.

For external SIR and teacup records, retain upstream provenance separately from
new local desktop evidence. Never relabel upstream output as produced by the
locally installed Stella version.

Computer-use automation may assist this protocol, but the retained files,
hashes, and manifest records are the evidence. A successful automation action
without those artifacts is not acceptance evidence.

- regenerated numeric comparison JSON and Markdown;

## Delivery Sequence

1. Vendor and pin the selected external fixtures with manifest and attribution.
2. Add failing feature-detection, strict-mode, preservation, and simulation
   guard tests.
3. Implement feature reports, compatibility exceptions, structural fragment
   preservation, and shared simulation preflight.
4. Extract the semantic signature and add structured round-trip differences.
5. Add reserved-identifier validation and migrate the bundled SIR template.
6. Upgrade the numeric comparator, parity report schema, and capability report.
7. Upgrade the agent protocol, runner, aggregation, and reporting to version 2.
8. Run automated gates and produce candidate desktop artifacts.
9. Complete Stella desktop exports and repeated personal-endpoint agent runs.
10. Update user documentation, changelog, release notes, and retained evidence.
11. Run final release gates and review all discrepancies before proposing the
    release commit.

Each implementation commit should keep tests and documentation for its behavior
in the same commit. Method-affecting changes are prohibited without a separate
user decision and corresponding documentation update.

## Explicit Non-Goals

- Implementing arrays, subscripts, or dimensioned variables
- Implementing nested XMILE models or compositional module instances
- Repairing malformed XML or undeclared namespace prefixes
- Replacing PySD or implementing a Stella-compatible simulation engine
- Changing numerical integration methods or adding scientific tolerances
- Adding Monte Carlo, global sensitivity, Bayesian calibration, or stock-initial
  calibration
- Adding HTTP transport, authentication, or multi-user session management
- Adding undo history, persistent edit journals, or a new model-diff MCP tool
- Expanding the built-in template catalog
- Treating three agent repetitions as an estimated population success rate

## Risks and Mitigations

### Preserving Unsupported XML Can Overstate Edit Safety

Mitigation: label unsupported features `preserved_only`, reject them in strict
mode and simulation, warn that renaming supported variables may not update
references inside preserved fragments, and avoid claiming semantic support.

### Upstream Corpus Drift or Licensing Ambiguity

Mitigation: vendor only pinned files, verify hashes, include the upstream MIT
license and attribution, and require deliberate manifest updates for every
upstream refresh.

### Numeric Evidence Can Be Misread as Equivalence

Mitigation: report raw discrepancies and alignment policy, retain source and
engine hashes, apply no inferred tolerance, and require explicit review of
non-zero results.

### Desktop Evidence Is Manual

Mitigation: keep generation and comparison scripted, minimize operator actions,
retain every resulting artifact, and keep desktop work out of headless CI
claims.

### Agent Runs Are Costly and Model-Dependent

Mitigation: keep paid runs manual, pin the protocol and requested settings,
record resolved backend metadata, report raw repetitions, and avoid universal
reliability claims.

## Definition of Done

The implementation is done only when all workstreams and release gates above
are satisfied, the capability matrix accurately classifies every retained
fixture, unsupported semantics fail early and clearly, numeric reports are
reproducible from committed inputs, agent protocol v2 evidence is retained, and
the documentation limits its claims to the evidence produced.
