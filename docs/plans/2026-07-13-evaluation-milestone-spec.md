# Evaluation Milestone Specification

Status: implemented on `codex/evaluation-milestone`

## Objective

Create a reproducible evidence layer for Stella MCP 0.11.0 that tests the
published stdio boundary, representative multi-tool workflows, XMILE
round-trips, optional simulation features, and files opened and saved by Stella
Professional.

This milestone establishes a deterministic protocol and application baseline.
It does not claim to measure free-form LLM planning quality.

## Scope

1. Exercise server initialization, tool/resource/prompt discovery, dynamic
   session resources, structured errors, and a build/save/read lifecycle through
   a real MCP stdio client.
2. Define versioned deterministic scenarios for model construction, template
   use, strict import/export, error recovery, simulation, scenario comparison,
   sensitivity analysis, and calibration.
3. Record environment metadata, protocol catalog identity, step results,
   durations, and artifact SHA-256 hashes in JSON; render a concise Markdown
   report from the same record.
4. Register Stella Professional-saved fixtures with application/version,
   source scenario, open/run checks, final run time, and visual review notes.
5. Verify supported model semantics across parse/export/reparse for every
   compatibility fixture.
6. Provide a strict CSV comparator for future Stella-versus-PySD numeric runs.
   It must reject mismatched time grids, perform no interpolation, report raw
   maximum absolute and symmetric relative errors, and apply no pass threshold.
7. Run the complete deterministic evaluation in the simulation CI job.
8. Exercise the declared minimum MCP SDK through the native stdio tests and
   correct the dependency floor if that protocol boundary fails.

## Scenario Contract

Scenarios are stored in `evaluation/scenarios.json` with schema version 1. Each
scenario declares:

- a stable ID and description;
- required capabilities such as `sim`;
- an ordered list of MCP tool calls;
- exact, non-empty, finite, and error expectations over structured results;
- expected artifact names.

The runner must fail for an unknown selected scenario, an unmet assertion, or a
missing expected artifact. A requested required capability must fail at startup;
an unrequested unavailable capability may skip only the affected scenarios.

## Desktop Acceptance

For each candidate fixture generated by the evaluator:

1. Open it in the installed Stella Professional application without a repair
   prompt.
2. Confirm expected stocks, flows, auxiliaries, and connectors are visible.
3. Run to the model's configured final time.
4. Save from Stella and re-import the saved file in strict mode.
5. Record application version, date, source scenario, and visual findings in the
   compatibility manifest.

Desktop review is operator evidence and cannot run in headless CI. The saved
fixtures and strict semantic round-trip checks are the durable regression gate.

## Numeric Comparison Contract

Numeric desktop parity requires two non-empty CSV exports: the PySD-backed MCP
run and Stella's own run. Column mappings and both time-column names are
explicit. The comparator requires numerically identical time grids and finite
values. It reports discrepancy metrics but does not infer a scientific
tolerance or classify pass/fail.

## Exit Criteria

- Native stdio lifecycle test passes.
- All deterministic scenarios pass with the `sim` extra and no skips.
- Stella-saved fixtures strict-import and preserve supported semantics.
- Desktop provenance is validated by tests and preserved by manifest sync.
- Core, simulation, MCP-floor, lint, evaluator, and package checks pass.
- Results document both confirmed behavior and unresolved evidence gaps.
